# Koofy Reader 구현·검증 계획

> 최신 실행 경로와 검증 결과는 [Readium 단일 리더 전환](readium-cutover.md)에 정리한다. 아래 G0~G5는 전체 제품의 검증 계획이다.

작성일: 2026-09-19  
기준 설계: [Koofy Reader 아키텍처](reader-architecture.md)

## 1. 패치 전 기준선과 현재 결과

2026-09-19 설계 검토 과정에서 기존 의존성을 오프라인 캐시로 복원한 뒤 다음 명령을 실행했다.

| 검사 | 결과 | 의미 |
| --- | --- | --- |
| `flutter analyze --no-pub` | 통과, No issues found | 패치 전 Dart 코드 정적 분석 |
| `flutter test --no-pub --reporter expanded` | 66개 통과 | 기존 단위·위젯 테스트 범위 |
| Android/iOS 앱 빌드·실기기 재현 | 이 검토에서 수행하지 않음 | 사용자가 보고한 구동 문제는 아직 재현·해결되지 않음 |
| 새 네이티브 Readium 구조 | 당시 미구현 | 아래 검증 계획을 수립한 기준 시점 |

테스트 통과를 실제 독서 동작의 정상 판정으로 확대하지 않는다. 기존 테스트에서 다루는 추정 위치 계산이나 내부 함수 일치가 실제 본문 표시의 정확성을 입증하는 것은 아니다. 최초 설계 문서화 단계에서는 앱 소스·의존성 버전을 변경하지 않았다.

이후 같은 날짜의 첫 통합 패치에서 Flutter 94개, Android 네이티브 7개, iOS 네이티브 5개 테스트가 통과했다. 양쪽 실제 Readium 본문·두 열 표시·지정 문단 복원을 검사했고, 서재의 미리보기 진입·복귀도 확인했다. 사용 환경과 APK 설치 제약, 구현 범위는 [G1 구현 기록](reader-g1-implementation.md)에 정리한다. 이어진 [메인 서재 패치](library-home-implementation.md)에서는 Flutter 전체 124개가 통과했다. 아래 행렬 전체, 실제 폴더블, 기존 기록 이전 및 출시 검증을 완료했다는 뜻은 아니다.

## 2. 단계와 완료 조건

### G0. 현재 실패 재현과 데이터 보존

- 연결 가능한 기기·시뮬레이터, OS, 빌드 모드, 파일을 기록한다. 구동 실패를 빌드 실패·시작 충돌·가져오기 오류·독서 중 오류로 구분한다.
- Android와 iOS의 초기 실행을 확인하고, 재현되는 증상의 로그와 최소 절차를 남긴다. iOS 서명·빌드 설정 문제는 독서 엔진 문제와 구분한다.
- 기존 책 목록·원본·읽던 위치·책갈피를 보존할 백업 및 테스트용 복제 방법을 정한다. 개인 책의 본문을 공개 로그·CI 산출물로 보내지 않는다.
- 기존 구조의 실패 사례를 새 구조에서도 실행 가능한 시나리오로 옮긴다.

완료 조건: 접근 가능한 환경에서 증상이 재현되거나, 재현하지 못한 환경·조건을 명시한다. 새 엔진 검증은 독립적으로 진행할 수 있지만 기존 실패가 해결됐다고 표시하지 않는다.

### G1. 두 플랫폼의 최소 독서 모듈

- Flutter에서 Android 네이티브 독서 화면과 iOS 네이티브 독서 화면을 각각 열고 닫는다.
- 동일한 작은 한글 EPUB으로 본문, 페이지 이동, 글자 크기, 한쪽·양쪽 배치를 확인한다.
- Pigeon의 접수·준비 완료·오류·닫힘 이벤트를 구분한다.
- Flutter 호스트가 inactive/paused가 되어도 독서가 이어지고, 화면 재생성 및 복귀 시 중복 호스트·세션이 생기지 않아야 한다.
- Readium, Pigeon, Flutter, 플랫폼 빌드 도구와 최소 OS의 검증한 버전을 기록한다.

완료 조건: 두 OS에서 같은 절차가 동작하고, 앱 복귀·다시 열기·지원하지 않는 파일 오류 처리가 확인된다. 한 플랫폼만 통과하면 G1 완료로 표시하지 않는다.

### G2. 위치·내구성·폴더블 검증

- 안정된 위치를 엔진에서 얻어 저장하고 초기 복원·재배치 동안의 임시 위치를 차단한다.
- 네이티브 체크포인트/변경 큐 → Flutter DB 트랜잭션 → 저장 확인 → 정리 흐름을 구현한다.
- 채널 응답 지연·재전송·이전 세션 이벤트·프로세스 종료를 주입해 검증한다.
- 실제 폴더블의 힌지, 접기/펼치기, 회전, 분할 화면을 검증한다. 시뮬레이션만으로 실기기 통과를 표시하지 않는다.
- 같은 콘텐츠의 Locator를 Android와 iOS 사이에 교환해 복원한다. 이 단계는 계정 서버 없이 테스트 데이터로 실행한다.

완료 조건: 아래 핵심 행렬의 필수 항목이 통과하고, 힌지 제약 및 대체 동작이 목표 사용자 경험에 맞는지 결정된다. 지원 범위를 제한해야 하면 설계와 앱 안내를 함께 수정한다.

### G3. TXT 변환과 파일 저장

- 원본의 앱 소유 저장, 인코딩 확인, 안정 문단 ID·href 생성, 변환 버전 관리, 중단 복구를 구현한다.
- 생성 EPUB을 EPUBCheck와 두 플랫폼 Readium으로 검증한다.
- CP949 등 모호한 인코딩, 중복 문단, 긴 문단, 빈 파일, 손상된 EPUB, 큰 파일을 포함한다.

완료 조건: 같은 원본·변환 설정의 논리적 주소가 반복 생성에도 같고, 변환 버전 변경은 새 리비전으로 처리된다. 지원 샘플에 본문 누락·잘못된 인코딩·주소 불안정이 없다.

### G4. 앱 이행과 기존 기록 이전

- 공통 서재·설정·파일 관리와 새 독서 모듈을 연결한다.
- Drift/SQLite 저장과 마이그레이션을 구현하고 기존 SharedPreferences 기록을 백업·변환한다.
- 기존 EPUB 평문 위치는 원본 Locator로 직접 복사하지 않는다. 문맥으로 매핑하거나 복원 불확실성을 남긴다.
- 새 엔진이 통과한 기능부터 기존 엔진을 대체한다. 자체 페이지 엔진을 영구적으로 두 벌 유지하는 것을 목표로 삼지 않는다.

완료 조건: 기존 책과 기록을 보존한 업그레이드 경로가 있고, 새 설치·이전 데이터·중단 후 재시도 모두 통과한다.

### G5. 출시 검증과 확장

- Android release 빌드와 iOS 기기용 빌드의 실행·서명·플러그인 연결을 확인한다. 분석·단위 테스트·양쪽 빌드를 CI에 넣는다.
- 실제 기기의 성능, 메모리, 접근성, 저장 오류를 확인한다.
- 하이라이트·메모, TTS, 동기화, PDF·만화 등을 기능별 검증 후 추가한다.

완료 조건: 출시 대상으로 선언한 포맷·OS·기기의 기능 행렬에 미해결 필수 실패가 없고, 측정한 성능이 사전에 기록한 목표 기기별 예산을 충족한다.

### 위치 검증 방법

화면 페이지 번호나 progression 값이 같다는 이유로 통과시키지 않는다. 테스트 책의 고유한 섹션·문단 ID와 인용문 문맥을 기준으로 목표 앵커가 현재 표시 범위에 있는지 확인한다. 동일한 문단이 반복되는 책도 포함한다.

두 플랫폼의 줄바꿈이나 좌우 배치가 달라도 해당 앵커가 복원되고 본문 누락이 없으면 정상일 수 있다. 사람이 실제로 어디를 보고 있었는지는 측정 대상이 아니다. 선택/TTS 위치가 없을 때의 기준은 설계 문서의 펼침 시작 정책이다.

### 테스트 책 집합

- 직접 작성하거나 테스트에 사용할 권한이 있는 한글·영문 EPUB/TXT만 저장소와 CI에 둔다.
- 짧은 책, 여러 장의 책, 매우 긴 단일 장, 긴 단락, 많은 빈 줄, 중복 문단, 이미지·각주·CSS가 있는 책을 포함한다.
- 이모지·결합 문자·한글 혼합 문자열을 넣어 문자 경계가 깨지는지 확인한다.
- 각 파일의 fingerprint, 인코딩, 생성/변환 버전, 기대 앵커를 함께 기록한다.
- 고정 레이아웃·RTL·세로쓰기 등 첫 출시 범위 밖의 파일도 지원 범위 안내와 실패 처리를 검사한다. 렌더링 지원 통과로 계산하지 않는다.

## 4. 성능 측정

실제 기기의 profile/release 환경에서 첫 열기 시간, 재열기 시간, 설정 변경 후 복원 시간, 페이지 전환 지연, 반복 독서 시 메모리와 CPU를 기록한다. debug 성능을 출시 수치로 사용하지 않는다.

글꼴·파일 크기·챕터 구성·화면 모드·캐시 상태·OS·기기 모델을 고정한다. 첫 열기와 캐시된 재열기를 분리한다. 엔진을 연속으로 열고 닫거나 접고 펼칠 때 메모리가 해제되는지 확인한다.

구체적인 지연·메모리 예산은 G1/G2에서 목표 기기와 실제 파일을 정한 뒤 기록하고 G5 전에 확정한다. 이 문서의 시점에는 60/120fps나 특정 메모리 상한을 검증한 사실이 없다. EPUBCheck나 단위 테스트로 성능 검증을 대체하지 않는다.

## 5. 실행 도구와 기록 양식

Flutter 공통 UI·저장은 Flutter test/integration_test, 네이티브 독서 화면은 Android 네이티브 UI 테스트와 XCUITest로 확인한다. Flutter integration_test만으로 네이티브 본문·OS 파일 선택기 내부의 모든 동작을 검증한다고 가정하지 않는다. 좌표 기반 조작은 가능하면 의미 있는 접근성 식별자와 본문 앵커 검증으로 보완한다.

빌드·단위 테스트는 CI에서 반복하고 실제 접힘·선택·접근성 검증에는 실기기를 포함한다. 자동화하지 못한 항목은 수동 검증 절차와 증거를 남긴다.

```text
검증 ID / 날짜:
코드 commit:
Flutter / Dart / Readium Kotlin / Readium Swift / Pigeon:
빌드 도구 / OS / 기기 / 빌드 모드:
파일 fingerprint / contentRevision / 변환 버전:
초기 위치 / 설정 / 창·힌지 상태:
실행 절차:
예상 앵커·저장 상태:
실제 결과: 통과 | 실패 | 미실행
증거: 테스트 로그, 위치 메타데이터, 필요한 화면 기록
제약·후속 조치:
```

로그에는 책 본문·메모 원문·실제 계정 토큰을 기본 기록하지 않는다. 테스트용 앵커 ID와 세션·리비전·순서 메타데이터로 복원 과정을 추적한다.

## 6. 판단 기준

전체 구조는 유지하되 아래 상황에서는 해당 선택을 수정한다.

- 목표 폴더블에서 요구한 양쪽 배치를 제공할 수 없으면 레이아웃 어댑터·지원 정책·엔진 대안을 다시 검토한다.
- 네이티브 전체 화면과 Flutter 호스트의 재생성/복귀가 안정되지 않으면 엔진 수명 또는 화면 호스트 방식을 수정한다.
- Locator 교차 복원이 불충분하면 콘텐츠 주소·변환 규칙·Locator payload를 보완하고 검증 전 동기화 기능을 출시하지 않는다.
- 저장 복구가 불충분하면 DB ACK·복구 큐를 수정한다. 단순 지연 시간 증가로 성공을 가정하지 않는다.
- 외부 래퍼가 필수 기능을 노출하지 않으면 자체 연결 모듈 안에서 공식 SDK를 직접 연결한다.

기술 선택의 성공 기준은 사용자가 실제 책을 읽고 돌아와 같은 위치에서 이어 읽을 수 있는지다. 도구 설치, 빌드 성공, 내부 함수 테스트 통과만으로 독서 리팩터링 완료를 선언하지 않는다.
